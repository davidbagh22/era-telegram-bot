## 1. Принцип принятия решений

Главный результат — участник **находит полезное мероприятие/задание, совершает действие, получает подтверждение и возвращается**. Число существующих экранов и пунктов меню не является метрикой успеха.

Каждое утверждение ниже помечается по доказательствам:

- **Есть в коде** — найдена реализация, но это не подтверждает работоспособность в production.
- **Согласно PR** — автор PR заявил о тестах/исправлении; требует независимой проверки и CI.
- **Не проверено** — нет подтверждения работоспособности; не означает «сломано».
- **Риск (гипотеза)** — участок кода с предполагаемым дефектом; до независимого теста это не установленная уязвимость.

Не собирать и не публиковать токены, содержимое профилей, телефоны, почту, реальные переписки или дампы БД в PR, логах и артефактах CI.

## 2. Проверенные факты и источники

- В `README.md` основной ветки перечислены: регистрация, админ-модерация, профиль/баллы/рейтинг, мероприятия, QR, проекты, задачи, департаменты, вопросы команде, панели администратора/лидера, рассылки и чат-модерация. **Это перечень заявленных возможностей, не результат end-to-end тестирования.**
- `README.md` сообщает «Mini App отключён», а открытые PR #317 / #318 изменяют `frontend/src/screens/admin/events/AdminEventCreatePanel.tsx` и `app/api/v1/admin_event_create.py`. **Выяснить, является ли README устаревшим и какой интерфейс реально доступен пользователям.**
- PR #318 (ветка `fix/era-topics-events-20261009`) содержит маршрутизацию в темы «Объявления» / «Оповещения», отключение групповых цитат, исправления публикации событий, новые тесты. Автор PR сообщает **74 целевых теста и frontend build**; это не доказательство production.
- PR #318 открыт и направлен в `main`, PR #317 также открыт. Исправление короткого описания, согласно описанию PR #318, включено в #318. **До слияния проверить отсутствие двойного применения или конфликтов.**
- `app/api/deps.py::get_session` фиксирует изменения в транзакции в конце HTTP-запроса.
- В коде ветки PR #318: `publish_event` делает явный `session.commit()` перед `_publish_broadcast`. Это ожидаемый порядок **для публикации**.
- В той же ветке `save_event_draft_step` вызывает `_notify_changed_event` до завершения транзакции запроса; `cancel_event` также уведомляет до окончания транзакции. **Гипотеза риска P1:** рассылка может объявить об изменении/отмене, которое не сохранится, или повториться при повторном запросе. Нужен тест, прежде чем менять реализацию.
- `app/services/admin_broadcast_service.py::send_personal_broadcast` делает внешнюю отправку до завершения фиксации записи `Broadcast` в текущем запросе. **Гипотеза риска P1** для аудита/повторов при ошибке коммита.
- `app/services/general_topics_service.py` сохраняет идентификаторы тем в `AppSetting` и не отправляет в основную ветку при отсутствии тем/прав. Настоящие настройки Telegram/Render не проверены.

## 5. Обязательная security-проверка

Подготовить data-flow карту `Telegram ↔ webhook/API ↔ application ↔ PostgreSQL/Redis ↔ exports/backups ↔ Render`. Для каждого вида персональных данных зафиксировать цель, согласие/основание, получателей, срок хранения, удаление, доступ, шифрование transit/at-rest, резервную копию и её удаление. Проверить:

1. Проверку Telegram initData/webhook-secret, истечение и отзыв access tokens, отсутствие dev-auth в production.
2. RBAC/IDOR на каждом обработчике callback/API, включая чужой event_id/user_id; негативные сценарии для ролей.
3. SQL/HTML/Markdown инъекции, размер payload и фото, ограничения скорости, flood control, Telegram callback replay.
4. Secrets exposure: CI/Render/env, redaction в ошибках, PII в логах, debug endpoints и экспорт.
5. Бэкап + успешное восстановление **в отдельной тестовой БД**, RPO/RTO и ответственность за хранение.
6. Dependabot/pip/npm audits с triage эксплуатируемости — не просто списком CVE.

Не утверждать юридическое соответствие без отдельной оценки применимых требований и политики обработки данных.

## 6. UX-пилот и продуктовая гипотеза

Персоны: **новый участник / активист / организатор / администратор**. Для каждой измерить с экранной записью тестового аккаунта: число переходов до ценности, время, процент успеха, ошибки и точки выхода.

Целевой путь: `/start → актуальная возможность → действие (записаться / взять задание) → подтверждение → результат/баллы → понятный следующий шаг`.

Минимальный главный экран — не более 4–6 верхнеуровневых действий: **Мероприятия**, **Задания**, **Мой профиль**, **Помощь**, **Организация/связь**; служебные пункты раскрывать по роли. Это **UX-гипотеза**, внедрять только после пилота и оценки существующих сценариев. Не удалить доступ к уже используемым функциям.

**Продуктовые метрики**, считать агрегатно, без сохранения содержания сообщений:

- `activation_7d`: доля зарегистрированных новых участников, совершивших за 7 дней хотя бы одно осмысленное действие (RSVP / взятое задание / заявку).
- `WAU`: уникальные люди с осмысленным действием за 7 дней, а не просто открытием /start.
- `retention_week2`: доля активированных пользователей, повторивших осмысленное действие на 8–14 день.
- `event_funnel`: просмотр → RSVP → фактическая посещаемость по QR.
- `task_funnel`: просмотр → принятие → подтверждение → одобрение модератором.
- `notification_health`: отправлено/ошибка/отписка/блокировка, без текста PII.
- `admin_event_TTV`: медианное время от начала мастера до опубликованной карточки без ошибки.

Baseline нужно получить до установки числовых целей; не выдавать вымышленные KPI за текущие показатели.
