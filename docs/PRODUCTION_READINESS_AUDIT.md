# ERA Platform — Production Readiness Audit

Дата: 2026-08-05. Baseline: `main` @ `e401b2f` (12-PR план завершён, PR #126
смержен). Полный `pytest -q`: 456 passed. CI (`Bot checks`): зелёный.

Этот документ — не теоретический список. У каждой находки есть статус:
**Fixed** (исправлено в рамках этого блока, со ссылкой на файл/коммит),
**Documented** (задокументировано, требует решения владельца — не технический
долг, а организационный/инфраструктурный вопрос), или **Backlog** (реальная
проблема, отложена по объёму работ — с чётким следующим шагом).

Важное наблюдение перед списком: часть механизмов, которые в типичном MVP
пришлось бы строить с нуля, в этом репозитории уже реализована зрело —
именно поэтому этот аудит не превращается в "перепишите всё". Что уже
хорошо (детали ниже, не повторяются в таблице находок):

- HMAC-проверка `initData` (`app/api/security.py`) реализована корректно:
  правильная схема Telegram (`WebAppData` secret → HMAC-SHA256 check-string),
  `hmac.compare_digest` для constant-time сравнения, проверка `auth_date`,
  никакого доверия к `initDataUnsafe`.
- Система допуска в общий чат (`app/services/chat_access_service.py`,
  `app/handlers/chat.py`) уже покрывает почти весь блок ТЗ "Дополнение":
  join-request approve/decline, авто-restrict новых участников
  (`welcome_members`), real-time модерация каждого сообщения
  (`moderation_gate` — удаляет сообщение неодобренного пользователя,
  повторно ограничивает его, шлёт ЛС с cooldown 300s против спама),
  синхронизация прав при одобрении/блокировке (`sync_user_chat_access`,
  вызывается из `rights_block6.py` при block/unblock и из
  `admin.py`/`panel.py` при одобрении регистрации), идентификация по
  Telegram ID везде, ID чатов — в конфигурации, а не в коде.
- `app/services/notification_service.py::broadcast_detailed` уже умеет:
  дедупликацию получателей, ограниченную параллельность, retry с
  экспоненциальной паузой на временные ошибки Telegram, разделение
  временных/постоянных ошибок, детальную статистику доставки.
- Автоматический ночной backup + verify-restore на изолированном Postgres
  уже работает в CI (`.github/workflows/database-backup.yml`) — checksum,
  30-дневный retention, восстановление проверяется реальным прогоном, а не
  предположением.
- Один Alembic head подтверждён при каждом PR (`0013_saved_opportunities`).
- `docs_url=None, openapi_url=None` — API-документация не раскрывается
  публично; секреты `.env.example` — плейсхолдеры, реальных значений нет.
- Все admin/leader endpoints уже используют backend-side `can_manage_*`/
  `is_full_admin` проверки (не только скрытие кнопок на фронтенде) — см.
  `docs/AUTHORIZATION_MATRIX.md`.
- Object-level authorization в целом соблюдается: каждый moderation/review
  endpoint грузит объект по ID и проверяет права до мутации, а не доверяет
  ID из фронтенда напрямую.

## Как читать "Fixed"

изменённых файлов — в блок-саммари PR.
