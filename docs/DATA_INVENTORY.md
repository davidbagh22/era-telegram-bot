# ERA Platform — Data Inventory

Фактическая инвентаризация полей, которые система реально собирает и
хранит — по коду (`app/database/models.py`, `app/database/partners.py`),
а не по намерениям. Каждое поле — с источником, целью, сроком хранения
(если определён) и статусом относительно ПДн.

⚠️ Это не юридический документ и не замена консультации с юристом.
Разделы 5–6 явно фиксируют, что решение по несовершеннолетним и тексту
согласия требует владельца платформы — см. также находки №16–17 в
`docs/PRODUCTION_READINESS_AUDIT.md`.

## 2. Портфолио, задания, мероприятия, возможности

|---|---|---|---|---|
| Текст/файлы результатов заданий | `TaskSubmission` | Проверка администратором, начисление баллов | Не определён — Backlog (см. раздел 7) | Нет |
| Файлы фото/видео/документов | не хранятся на сервере, только `file_id` Telegram | Отображение через Telegram API по требованию | Управляется Telegram, не этим приложением | Telegram (уже используется пользователем как канал загрузки) |

## 3. Минимизация — что уже сделано правильно

- Response-схемы API (`*Out` Pydantic-модели) во всех эндпоинтах уже
  ограничивают, какие поля `User`/`Project`/`Task` возвращаются наружу —
  нет ни одного эндпоинта, отдающего "весь ORM-объект как есть" (проверено
  при аудите, см. `docs/PRODUCTION_READINESS_AUDIT.md`, находка №9).
- Файлы никогда не проходят через сервер как raw upload — только через
  Telegram `file_id` (находка №10 там же) — это уже минимизация по
  архитектуре, не по политике.
- Массовые выгрузки (Excel-экспорт, `excel_service.py`) доступны только
  через админ-панель бота, не через Mini App API — не увеличивает
  поверхность атаки за счёт нового публичного эндпоинта.
- Рейтинг участников (`GET /api/v1/leaderboard`,
  `app/services/leaderboard_service.py`) — Mini App-версия давно
  существующей функции бота "🏆 Рейтинг" (`cabinet:rating`,
  `app/handlers/participant/cabinet.py`), не новая поверхность
  раскрытия данных: то же имя/фамилия + баллы, тем же approved/не
  заблокированным участникам, что бот уже показывает в чате. Новых
  полей не добавлено и согласие не расширено.

## 4. Что не сделано (честно, без замалчивания)

- Нет отдельной таблицы `consent_log` — согласие хранится только как
  `bool` без версии текста, даты/времени и типа согласия (регистрация vs.
  публикация фото/видео отдельно). См. находку №16.
- Нет отдельного согласия на публикацию фото/видео в портфолио/на сайте —
  сейчас предполагается, что общее согласие при регистрации покрывает всё.
  Это решение владельца платформы, не техническое.
- Нет определённых сроков хранения (retention policy) для заявок,
  отклонённых заявок, файлов, портфолио, отчётов, административных
  действий и резервных копий отдельно от Postgres backup policy (30 дней
  для самого бэкапа — не то же самое, что срок хранения данных
  пользователя внутри активной базы).
- Нет реализованного самообслуживаемого экспорта/удаления данных
  пользователем (self-service). Технически администратор может вручную
  удалить/анонимизировать запись через прямой доступ к БД — процесс не
  формализован как отдельная функция в этом блоке.

## 5. Согласие на обработку персональных данных

Текущее состояние: `personal_data_consent: bool` остаётся полем, которое
реально проверяется в коде — это не изменилось. **Обновление (PR18):**
добавлена таблица `consent_log` (`app/database/models.py::ConsentLog`,
миграция `0014_consent_log`) и `app/services/consent_service.py` —
`record_consent()` теперь пишет отдельную запись (Telegram-пользователь
через `user_id`, тип согласия, версия политики, дата/время, источник
bot/miniapp) при каждой регистрации, дополнительно к булеву полю, не
вместо него. `latest_consent()` позволяет прочитать последнюю запись по
пользователю и типу согласия.

**Важно — это техническая основа, не решённый вопрос соответствия**:
`policy_version` сейчас равен константе-плейсхолдеру
(`consent_service.CURRENT_POLICY_VERSION = "unset-v1"`), а не реальному
тексту политики. Ничего в `consent_service.py` не пишет, не проверяет и
не подтверждает содержание политики — таблица фиксирует *события*
согласия, а не определяет, что именно считается согласием. Как только
появится реальный текст от владельца/юриста, достаточно сменить одну
константу — все последующие записи будут ссылаться на новую версию, а
старые записи останутся привязаны к той версии, под которой согласие
реально давалось.

**Что всё ещё нужно для полноценного соответствия** (не сделано, требует
владельца, не техники):

1. Реальный текст политики конфиденциальности и согласия — от владельца
   платформы, при необходимости согласованный с юристом.
2. Отдельное согласие на публикацию фото/видео, если оно требуется по
   бизнес-логике (сейчас портфолио отображает загруженные материалы без
   отдельного разрешения на публичный показ) — технически `consent_type`
   уже поддерживает произвольные типы согласия, добавить второй тип
   несложно, когда появится решение, что именно спрашивать.

## 6. Несовершеннолетние пользователи

Поле `birth_date`/`age` собирается, но по-прежнему **нигде не влияет на
доступ к каким-либо функциям** — ни при регистрации, ни при согласии.
Это означает:

- Платформа технически не проверяет и не ограничивает доступ по возрасту.
- Если среди участников ЭРА есть лица младше 18 лет, для их данных может
  требоваться согласие законного представителя согласно применимому
  законодательству — это решение и юридическая ответственность владельца
  ЭРА, **не может быть закрыто одним техническим PR**.

**Обновление (PR18) — техническая часть подготовлена, не активирована**:
`app/services/minors_service.py::is_minor(age)` — чистая функция без
побочных эффектов, возвращает `True`/`False`/`None` (неизвестно, если
возраст не указан). Единственное текущее использование — одна
информационная строка в карточке администратора
(`app/services/admin_user_card.py`, "Несовершеннолетний (по анкете)"),
видимая только администраторам, ничего не блокирующая и не меняющая ни
для кого доступ или сценарии. Это ровно то, что просил не путать ТЗ:
техническая возможность видеть данные — да; юридическое решение о том,
что с этим делать (отдельное согласие представителя, ограничение
видимости полей, отказ в регистрации) — явно нет, и не должно молчаливо
считаться реализованным.

Явно фиксируем: до появления решения владельца по этому пункту, платформу
**нельзя** описывать как полностью соответствующую требованиям к
обработке данных несовершеннолетних.

## 7. Рекомендованные сроки хранения (предложение, не решение)

Ниже — рабочее предложение для обсуждения с владельцем, не внедрённая
политика:

| Данные | Предлагаемый срок |
|---|---|
| Отклонённые заявки на регистрацию | 12 месяцев с даты отклонения |
| Отклонённые заявки на возможности/задания | 12 месяцев |
| Audit log | не менее 24 месяцев (подотчётность) |
| Файлы (через Telegram, вне контроля приложения) | управляется политикой хранения самого Telegram |
| Резервные копии БД | уже реализовано — 30 дней (`docs/BACKUP_AND_RECOVERY.md`) |
| Активные пользовательские данные (профиль, портфолио) | пока пользователь активен + разумный льготный период после архивации |
