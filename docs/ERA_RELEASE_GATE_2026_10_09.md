# ЭРА — чек-лист выпуска и протокол проверки (аудит, 09.10.2026)

**Назначение:** безопасная приёмка PR #318 и последующих PR на действующем Telegram-боте.  
**Положение на 09.10.2026:** никаких production-команд и массовых тестовых рассылок данным документом не запускается.

## 0. Разграничение полномочий

- Создание ветки, PR, чтение кода и локальные тесты — допустимы.
- Production merge/deploy, изменение тарифов Render, чтение секретов и запуск сообщений пользователям — **только отдельное явное разрешение владельца**.
- Для проверки Telegram использовать тестовую группу/учётные записи, без копирования приватных данных участников.
- Удаление существующих записей ради теста, ручная чистка таблиц или изменение реальной конфигурации без backup запрещены.

## 1. Before merge — код и CI

- [ ] Сверить HEAD/base каждого PR, список изменённых файлов и пересечение PR #317 / #318.
- [ ] Полный CI green (не только целевые 74 теста из описания PR #318).
- [ ] `python -m pytest -q` на разрешённом окружении с конфигурацией тестовой БД.
- [ ] `python -m compileall -q app tests` и выбранные lint/typecheck jobs.
- [ ] `npm run build` из `frontend` при наличии актуальной сборки.
- [ ] `alembic heads` и smoke upgrade/downgrade **на копии** БД; не применять опасные миграции к production.
- [ ] Проверить, что API/бот/фронтенд используют одну актуальную схему события.
- [ ] Безопасность зависимостей + проверка diff на токены, PII, служебные URL.
- [ ] Путь создания/публикации/отмены: только имеющий права администратор может менять статус.
- [ ] Отрицательные тесты: роль participant, чужой event/user ID, двойной callback, конкурентные запросы.
- [ ] Дедупликация автоматических уведомлений после повторного вызова scheduler.

## 2. Staging — критические E2E сценарии

Использовать только тестовые личности, тестовый чат и тестовые события.

| № | Шаг | Ожидаемое доказательство |
| --- | --- | --- |
| E1 | Открыть бота как новый пользователь, пройти регистрацию и согласие | Завершение без ошибки, видимое следующее полезное действие |
| E2 | Пройти регистрацию как администратор нельзя; participant вызывает чужой callback | 403/отказ, административные данные не раскрыты |
| E3 | Администратор создаёт черновик, заполняет **только короткое описание**, перезапускает клиент | Данные сохраняются, полное описание подставляется при публикации |
| E4 | Дважды нажать «Опубликовать» и обновить страницу | Одна запись мероприятия, одна автоматическая публикация |
| E5 | Симулировать Telegram timeout **после commit** | Событие остаётся опубликованным, failure logged без PII |
| E6 | Изменить дату / место опубликованного события и повторить запрос | Новые поля persisted; одна согласованная запись о изменении, без старых данных |
| E7 | Отменить мероприятие дважды | Нет повторных или несогласованных объявлений |
| E8 | Participant записывается; другой достигает capacity/waitlist; QR checked дважды | Лимиты выдержаны, начисление баллов ровно один раз |
| E9 | Отправить **тестовую** общую рассылку и тестовый сегмент | Общая копия в «Оповещения», сегмент не опубликован публично |
| E10 | Сгенерировать событие, изменение, напоминание, отмену | Сообщения только в «Объявления», idempotency keys уникальны |
| E11 | Включить scheduled channel content в тестовой среде | Канальный пост по расписанию, **ноль** сообщений `chat_quote` в общий чат |
| E12 | Открыть FAQ, задания, опрос, профиль с кнопок | Нет сломанных callback, есть возврат к полезному действию |

## 3. Telegram forum acceptance (#318)

- [ ] Целевой чат действительно `supergroup`, **Topics включены владельцем**.
- [ ] Бот администратор с правом `can_manage_topics`.
- [ ] В БД корректные `general_forum:<chat_id>:announcements` и `general_forum:<chat_id>:notifications`; ID соответствует существующим темам.
- [ ] Если тема уже существует, её ID привязан без дублирования. Не создавать повторные темы при каждой перезагрузке.
- [ ] При отсутствии прав ошибка видна оператору и **нет fallback** публикации в общий поток.
- [ ] В **группе** inline button использует обычную URL; не `WebAppInfo`.
- [ ] Частные уведомления RSVP, анкеты и роли не публикуются в общую тему.
- [ ] Для фото-афиш сохранён механизм отправки, корректны caption/message_thread_id.
- [ ] Для удалённой темы предусмотрена ручная перепривязка, а не бесконечное автосоздание.
- [ ] Предыдущие исторические сообщения не перепубликуются.
- [ ] Проверен журнал `NotificationDelivery` и отсутствие новых групповых `chat_quote`.

## 4. Security/backup/operations gate

- [ ] Владельцем Render подтверждены **workspace, web service, БД, Redis, production branch/commit**.
- [ ] Известны автоматический deploy policy, способ revert и сохранённое предыдущее изображение/commit.
- [ ] Бэкап БД сделан **без выгрузки в PR/CI**, восстановлен в отдельную тестовую БД и проверены ключевые таблицы.
- [ ] Настроены журнал ошибок без персональных данных, alerts на webhook 5xx, DB errors, notification delivery failures и очередь задач.
- [ ] Проверен TLS и политики хранения/шифрования в доступных инфраструктурных компонентах; то, что неизвестно, явно отмечено.
- [ ] Проверены RBAC/IDOR, webhook secret, отсутствие `dev_auth_enabled` в production, ограничения скорости.
- [ ] Есть on-call контакт владельца и безопасный порядок rollback.
- [ ] Зафиксирована фактическая месячная стоимость сервисов Render и лимиты с запасом; тариф **не изменён автоматически**.

## 5. Canary и rollback

1. После отдельного разрешения — deploy на staging и smoke E1–E12.
2. При отдельном разрешении на production — зафиксировать commit SHA, backup point, владельца и время.
3. Начать с одного тестового события и ограниченного круга уполномоченных пользователей. **Никаких массовых рассылок по умолчанию.**
4. Проверить error rate, сохранность событий, точность тем/кнопок и отсутствие дублей.
5. При блокирующем дефекте отключить только новый путь отправки/откатить deploy по согласованной процедуре, **не удалять живые данные**.
6. После релиза документировать фактические результаты, ссылки на CI, staging evidence и production health.

## 6. Итоговый шаблон протокола

| Поле | Заполнить при фактической проверке |
| --- | --- |
| PR / commit SHA | Не заполнено |
| Владелец приёмки | Не назначен |
| Проверенные окружения | Только чтение кода GitHub в рамках подготовки документа |
| Full CI status | Не подтверждён окончательный результат |
| Бэкап: дата и restore test | Не подтверждено |
| Форум: is_forum и can_manage_topics | Не проверено |
| P0 открытых | Не определено до завершения security audit |
| Ошибки, backlog P1/P2 | См. `ERA_AUDIT_BASELINE_2026_10_09.md` |
| Время / путь участника, UX-пилот | Не измерены |
| WAU / activation_7d / retention_week2 | Нет baseline |
| Разрешение владельца на deploy | **Не дано в рамках этого PR** |
| Финальный статус | **НЕ ГОТОВО / ПРОВЕРКИ НЕ ЗАВЕРШЕНЫ** |

Использовать формулировку «готово» только после прохождения всех приёмочных gate. Документация сама по себе не делает бот безопасным и не доказывает, что он работает в production.
